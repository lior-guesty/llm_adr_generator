# Guidelines for Generating Architecture Decision Records (ADRs)

## Purpose
This document provides guidelines for LLMs to generate comprehensive Architecture Decision Records (ADRs) based on identified design decisions, creating standardized documentation of architectural choices.

## Input Parameters
- 'content': all context of initial analysis and design discussion. In the <content> tags below.

## Output
For each decision in the input list:
- A separate ADR file in Markdown format with a standardized structure
- Filename format: `ADRXXXX-Decision-Title.md` (where XXXX is a sequential number)

## ADR Structure

Each ADR should follow this structure:

```markdown
# ADRXXXX: [Decision Title]

## Context
[Description of the context, constraints, driving forces and problem that motivated this decision]

## Decision
[Description of the decision that was made]

## Consequences
[Description of the consequences, both positive and negative, of the decision]
```

## Process

### 1. Preparation
- Review the complete list of decisions to understand relationships between them
- Sort decisions by importance and dependency (fundamental decisions first)
- Assign sequential numbers to each decision (ADR0001, ADR0002, etc.)
- If knowledge graph is available, query for additional context about each decision

### 2. For Each Decision, Generate Context Section
The Context section should:
- Clearly state the problem being addressed
- Provide background information necessary to understand the decision
- Describe constraints that influenced the decision
- Outline alternatives that were considered
- Include direct quotes from source materials when they provide clear context
- Explain technical or business factors that influenced the decision
- Be comprehensive yet concise (typically 3-6 paragraphs)

Process:
1. Extract relevant discussion segments mentioning the problem or need
2. Identify constraints mentioned in the discussion
3. List alternatives that were considered
4. Note any evaluation criteria used to assess alternatives
5. Organize into a coherent narrative that leads logically to the decision
6. Include direct quotes when they clarify the context

### 3. For Each Decision, Generate Decision Section
The Decision section should:
- Clearly and unambiguously state what was decided
- Include direct quotes from source materials that clearly state the decision
- Provide specific technical details when relevant
- Avoid ambiguity or hedging language
- Be definitive about what approach was selected
- Be concise (typically 1-3 paragraphs)

Process:
1. Extract explicit decision statements from the source materials
2. Format as a clear, declarative statement
3. Include relevant technical specifics
4. Reference any conditional aspects of the decision
5. Note the time frame or project phase if the decision has temporal limitations

### 4. For Each Decision, Generate Consequences Section
The Consequences section should:
- List both positive and negative consequences of the decision
- Include immediate implications and long-term effects
- Address impacts on quality attributes (performance, maintainability, security, etc.)
- Note trade-offs accepted as part of the decision
- Identify technical debt or limitations introduced
- Describe how the decision affects other system components
- Include implications for future development or evolution
- Be balanced and realistic (typically 4-8 bullet points or paragraphs)

Process:
1. Identify explicit consequences mentioned in source materials
2. Infer additional consequences based on technical knowledge
3. Ensure coverage of immediate and long-term effects
4. Consider implications for system qualities and other components
5. Validate that identified consequences are realistic and relevant

### 5. Knowledge Graph Integration (if available)
- For each decision, query the knowledge graph for:
  - Related entities that may be affected
  - Similar previous decisions
  - Components that implement or are affected by the decision
  - Constraints or requirements related to the decision
- Use this information to enrich all sections of the ADR
- Identify relationships between decisions that should be cross-referenced

### 6. ADR Finalization
For each ADR:
1. Review for completeness and accuracy
2. Ensure clear connection between Context, Decision, and Consequences
3. Check for consistency with other ADRs
4. Format according to Markdown conventions
5. Create file with appropriate naming convention: `ADRXXXX-Decision-Title.md`

### 7. Cross-Linking (Optional)
- Add references between related ADRs
- Ensure consistent terminology across ADRs
- Consider adding a status field to each ADR (Proposed, Accepted, Superseded, etc.)

## Examples

### Example Context Section
```markdown
## Context

The Bill of Materials (BOM) system requires persistent storage for BOM documents and data snapshots. During our design discussions, we considered multiple storage options to implement a hash tree structure that would allow us to efficiently identify differences between BOM versions.

As documented in our design notes:

> "BOM Store options:
> * Should essentially implement a hash tree, so we can later identify diffs easily and in a performant manner.
> * The tree depth is bound by a constant, at most 3-4 levels (see structure above).
> * Options
>    * Relational db, implementing a tree
>    * Mongo, implementing a tree.
>    * Graph DB
>    * DynamoDB
>    * Git.
>       * Has the functionality of keeping changes built-in. So may save us the calculation of hashes of the tree."

Each option presented different trade-offs:

1. **Relational databases** would provide ACID guarantees and transaction support but might be complex for tree structures.
2. **MongoDB** would offer document-oriented storage fitting our JSON/TOML documents but require additional work for tree traversal.
3. **Graph databases** would naturally represent tree relationships but add a new technology to our stack.
4. **DynamoDB** would provide scalable, managed storage but with potential complexity for tree operations.
5. **Git** would offer built-in versioning and diffing but might not be optimized for our specific use case.
```

### Example Decision Section
```markdown
## Decision

We decided to use Amazon S3 for storing BOM documents and data snapshots. As noted in the design:

> "BOM Calculator: reads DLog records and output a complete BOM document. Only for entities for now. Persists the document in S3. BOM document as JSON or TOML."

And for data snapshots:

> "Data snapshot store is S3. All schema described is in the BOM DB."

This decision aligns with our simplified initial approach to store complete documents rather than implementing a complex granular element store with sophisticated hash tree operations from the beginning.
```

### Example Consequences Section
```markdown
## Consequences

The choice of S3 for BOM document storage has several consequences:

1. **Operational Simplicity**: S3 is a well-established, highly available storage service that requires minimal operational overhead, aligning with our need for a straightforward initial implementation.

2. **Cost-Effective Storage**: S3 provides cost-effective object storage suitable for document-based artifacts like our BOM documents and snapshots.

3. **Limited Query Capabilities**: S3 has limited native query capabilities compared to database options, which may impact our ability to perform complex queries directly against stored BOMs without additional processing.

4. **Versioning Support**: S3 offers built-in versioning capabilities that we can leverage for tracking BOM document changes over time, partially addressing our diffing requirements.

5. **Integration Simplicity**: S3 integration is straightforward and well-supported across our technology stack, simplifying implementation.

6. **Future Migration Path**: Should we later decide that S3 is insufficient for our needs, we can migrate to a more sophisticated storage solution while maintaining S3 as an archive or backup.
```

## Common Pitfalls

- **Generic Context**: Failing to provide specific technical details about the problem and alternatives
- **Ambiguous Decisions**: Not clearly stating what approach was chosen
- **Missing Consequences**: Omitting important implications, especially negative ones
- **Lack of Quotes**: Not using direct quotes from source materials when they would add clarity
- **Inconsistent Terminology**: Using different terms for the same concepts across ADRs
- **Insufficient Technical Detail**: Being too vague about implementation details
- **Overly Technical**: Including too much implementation detail that doesn't affect the architectural decision
- **Scope Creep**: Including multiple decisions in a single ADR
- **Narrative Gaps**: Failing to connect context logically to decision and consequences
- **Future Speculation**: Including speculative future decisions rather than focusing on what was actually decided
