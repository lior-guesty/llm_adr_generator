Bill of Materials


Definitions and Existing Design




Entity description: a logical boundary around a bounded context. Will translate in a lot of cases to different physical deployments.
Infrastructure bill of materials: cross cutting concerns, graph of db manifests.


A Unit: the piece of code (usually terraform) for deploying a specific type of workload.


We refer to any object described in the BOM as a BOM element - any object that is relevant to be deployed in the system and may have state/configuration that need to be preserved when re-creating the system.
BOM elements include entities, infrastructure elements (DBs, Kafka topics, Gateways), Units.


A deployment of an entity is defined by:
* The units used to deploy the identities and infrastructure elements.
* The code to be deployed, per identity
* The database to be deployed
   * Type of DB
   * Initial data snapshot.
* The manifest defining deployment parameters.




Infrastructure Deployment
Currently, deployment of a system consists of the set of entities deployed (and their respective identities), as well as infrastructure for running the system.
The infrastructure is:
* API gateway definitions (Kong).
* Database definitions
* Publications and subscriptions (topics and their consumers).
   * These are Kafka definitions. RabbitMQ (RMQ) is stateless, so there’s no per-environment setup of RMQ.


Originally, databases were not exclusively owned by entities. This resulted in a situation where deployment of databases is decoupled from entity definitions. 
Newer elements tend to own db definitions. Kafka topics are usually tied to DB definitions (either for CDC or business events), and therefore Kafka definitions are defined with DB definitions.
Direct Kafka usage (writing directly from code to Kafka, not through the outbox pattern) is expressed in the entity definition.
There is an option to specify ownership of a database (or a cluster) by a specific entity.
Bill of Materials - Content and Structure


Identifying Changes
We expect a BOM for a given environment to become a large document, with different elements changing at different times (for different reasons). This will result in a need to easily identify when a given BOM element has changed, its version.


In order to identify change we could maintain a running version number per BOM element, or somehow derive the version based on semantically relevant properties of the BOM element. By “semantically relevant” we refer to any type of change that changes the behavior of the deployed element. 
For example, a change in a deployment unit’s code may result in a change of the deployment. But if the change is simply a whitespace or comment added, this isn’t relevant to the deployed system’s behavior. We will consider a unit’s code changed if there’s a new git commit of the unit’s code.


Keeping a running number per number per element is less efficient - it requires maintaining extra metadata, and also requires human intervention (someone needs to decide that a version is increased). It has the benefit of implying an order of changes. 
Deriving the version by hashing on a set of relevant attributes is easier to programmatically add generically. It assumes of course the chosen hash function provides good distribution. It also allows easy detection of relevant changes.


For now, we’ll proceed with using hashes to denote versions of BOM elements. It could also help in identifying changes in composite elements (e.g. by using a hash tree). We expect this to be relevant when we will need to identify conflicts and apply subsets of a complete BOM[1].


For each BOM element we will define the set of elements that are semantically relevant to constitute a version change and hash those - its version identity. In some cases, we should consider using built-in definitions, e.g. in Terraform-based elements.




BOM Model


Assumption 1: The BOM needs only maintain the inventory and versions of different components used in order to re-create an environment in a consistent manner. It does not need to maintain the actual content of the different elements. We therefore assume that all manifests, configuration files, code artifacts etc. are available and deterministically reference-able. The BOM document/db needs to maintain only the references to the actual elements changed.


Assumption 2: Deployment is always that of a complete entity, with all of its identities. This implies that a change in a specific identity derives a change in the entire entity. We never deploy a subset of the entity’s workloads (identities). The BOM can therefore be kept at the entity level of granularity.


When looking at the expected usage of the BOM, we derive several design principles for the design of the BOM and relevant processes.


Design Principle 1: BOM Document Describes a Complete System
The BOM document is a complete description of the system’s functional elements. Every relevant element that is necessary for recreating the environment should be part of the DOM.
Note that this does not exclude the possibility to design processes that transmit or apply subsets of a BOM document, e.g. applying specific changes. It just means that in order to consistently and reliably describe a functional system, the BOM document must include all relevant components.


Design Principle 2: BOM Immutability
The BOM document is Immutable 
This means that changes to a BOM, however minor, in effect derive a new BOM document. This makes detecting and tracing changes easier. 
Note that the BOM document is essentially a document of pointers (assumption 1), so in order for the BOM to be truly immutable, it relies on the content reference itself to be immutable as well, and the pointer to point to a specific version of it. Using concrete version hashes allows us to achieve this.




We continue to define the basic elements of the model.
A schematic view of the object model for a BOM definition (source):
  





A BOM Element is a versionable element that affects the functionality of a deployed system. It has a hash uniquely representing its content. 
Its name uniquely identifies it globally, across versions and deployments. In other words, we should be able to identify different versions of the same element from different BOM documents.


A Content Reference (ContentRef) is a structure type defining the coordinates of where to find the content of a given BOM element:
1. Location (a string): the path to the content of the element.
   1. Usually a path under guestyorg.
2. blob sha (a number): the version indicator of the artifact used to identify its version. For example, a hash over the specific content of the artifact referenced.




A Deployed Element represents any BOM element that is deployed in the system. It is some application of a deployment functor on a specific change functor.
It has: 
1. A reference to an inventory artifact describing what is to be deployed (inventoryRef).
2. A reference to the functor used to deploy it (functorRef).
3. A change context (changeContext) - the set of parameters used in the application of the functor when deploying the element. This is information provided to the functor when applying it, and is not available in other places (and therefore not referenceable). It’s a general property bag (key-value dictionary).




An Artifact-Based Element is a BOM element representing the inclusion of some external artifact in the bill of materials. 
It has a content reference, pointing to where the content of the element resides - artifactRef.


A Deployment Functor is a BOM element identifying a function to deploy a specific type of element. It maintains the list of elements using this functor. Note different deployed elements may use different versions of the same functor. The name of the functor uniquely identifies it. Its content hash represents any change in any of the deployed elements.

A deployed element has two content references:
1. The contentRef points to the actual element’s content. This is usually the repo path containing the code of the element (and entity).
2. The manifestRef pointing to the manifest in the platform inventory. This contains the deployment variables used for deploying the entity.


The current mechanism for deploying components in Guesty works by iterating over units in the inventory (the functors) and applying them to all platform inventory elements (the other Deployed Elements). We therefore construct the BOM document with the root (Bill of Materials) enumerating the functors used, with each functor pointing to the list of elements it deploys.
Content Hash
The BOM element maintains a version indicator for the element represented. This is a number, resulting from a hash calculation over all attributes relevant to determine the functionality of the said element. It therefore reflects the content of the element, and can be used to quickly determine whether two elements differ or not.


The hash reflects the properties relevant to functionality offered by the said element. A detailed design should specify in detail the attributes to hash per element type.


Calculating the Hash


We define the hash calculation over each object in the model.
The general principle is to hash properties that might reflect a change meaningful to a change in behavior, to reflect a potentially different behavior in the system.
The hash calculation should be deterministic so two objects that represent an unchanged behavior will map to the same hash (“look the same”).


We use an MD5 hash function, hashing to 32 bytes. Since its implementation is widely available. It provides a good enough hash to avoid collisions and does not couple us to a specific implementation.


For an artifact BOM element[2], the hash is defined as: 




artifact_element.content_hash := MD5(inventoryRef.blobSha + ":" + functorRef.blobSha + ":" + artifactRef.blobSha)

The hash of the functor (pointing to the deployed elements):


deployed_elements_content_hashes := el.content_hash for el in deployed_elements //sorted by name, ascending
functor.content_hash := MD5(functor.name + deployed_elements_content_hashes)

Note:
1. For functors that have no deployed elements in a given document, the content hash will be simply a hash of the functor name, i.e. constant, but different from other similar (“empty”) functors. This is intended.
2. The deployed elements' content hashes are sorted by name in ascending order and concatenated. Order is important to keep hashes deterministic. So unchanged functors in different BOM documents should result in the same hash. This is intended.

Flows
We continue with describing the basic flows for creating and using a bill of materials.
The basic building blocks are:


A BOM Calculator is the component that maintains and defines the actual BOM model. This is what builds the BOM document (using the described model), and calculates differences between different BOM instances.


The BOM Store maintains different instances of BOM documents. The BOM Store “lives” in the context of a specific environment, and maintains its bill of materials, including potentially its history. 


The Environment Deployer (Env Deployer) is the component that, given a specific BOM (or some designation of a BOM), can create or update a given environment with the given BOM. It cooperates with the BOM Store to figure out the correct BOM instance, and then acts on it, potentially using the BOM Calculator to figure out the necessary elements to deploy/update.  


Out of these components, the calculator and the deployer are stateless components. All of the relevant state is maintained in the BOM store (for a given environment), or potentially in some other repository (globally); for example, a git repository maintaining BOM documents for different test scenarios etc.


Creating a BOM


  



The Bill of Materials is maintained in the environment, in the BOM Store. It is calculated and updated on every deployment of a new element (an invocation of a Deployment Functor).


This assumes that all changes to an environment are done using deployment functors, or through some other mechanisms that take care to update the BOM store. Breaking this assumption will lead to a BOM store that is out-of-sync with the actual environment it represents.


Each valid change updates the BOM store, essentially creating a new BOM instance (since it’s immutable). While the basic functionality doesn’t require more than accessing the latest version, it’s possible that future use cases will require querying and accessing past versions of the BOM; e.g. for troubleshooting or experimenting.


Creating a New Environment Based on an Existing Flow


  



Given a BOM instance obtained by the developer, e.g. from some git repo, a test db or a different environment, the developer can execute the environment deployer with the entire BOM. In this case, the environment deployer creates a new environment, with the given name and BOM details (and other relevant information - pending more detailed design).
The process of deployment (activation of functors), takes care to update the environment’s local BOM store so the environment maintains its relevant BOM.
Applying a BOM to an Existing Environment


  



The process of applying a BOM to a given up and running environment is similar to creating a new one. The difference here is that we would like to only apply the changed elements, and not override the entire existing BOM with already deployed elements. This is both for achieving better process performance as well as allowing us to apply only subsets of a BOM - opening the door to more advanced scenarios of cherry picking elements in an environment or “merging” two separate environments.


The environment deployer uses the BOM calculator to identify the difference between the existing BOM and the one requested to be applied. Note that the existing BOM may be newer than the one being applied.


BOM Diff
Here is a rough outline of an algorithm to find out the difference between 2 given BOM instances - BOMnew (BN) and BOMold (BO).
Which of the two instances is considered new is up to the invoking application, or to be identified automatically by the createdAt time stamp (in which case it cannot be the same timestamp).


Node Identity 


For purposes of identifying the same node in two separate instances, we define the identity of a node as the location attribute of its manifestRef.
Assumption: the location of an artifact BOM element uniquely identifies the element. 
⇒ There cannot be 2 elements with the same location in its manifest reference in a valid BOM instance.


Finding the Difference


For notation we will use the ‘-’ sign to signify set difference, under the definition of identity given above.


The basic idea of finding the difference is to find:
1. The new functors in BN
2. The removed functors in BO 
3. The new, removed and changed elements for each changed functor in BN 






New functors ≔  BN.functors - BO.functors 
Removed functors ≔ BO.functors - BN.functors
Changed functors ≔  
 i.e. we consider a functor changed if it exists (per its identity) in both BOM instances, and has a different content hash. 


For each changed functor, we calculate its:
1. The new elements in BN
2. The removed elements in BO 
3. The changed elements.


For a given changed functor F, where FN and FO represent its new and old versions respectively: 
New elements ≔  FN.deployedElements - FO.deployedElements 
Removed elements ≔ FO.deployedElements - FN.deployedElements
Changed elements ≔  
 i.e. we consider a deployed element changed if it exists (per its identity) in both BOM instances, under the same functor, and has a different content hash. 
We assume the content hash already represents the content reference (with its commit), the element’s identity and any other extra data, e.g. environment variables.


The diff includes:
1. The new functors
2. The removed functors
3. Changed elements with their respective new/removed/changed elements.


New and old functors/elements should include their entire content.
Changed functors/elements should include their new and old content as part of the diff.

function normalizeAndHash(changeContext)

Updated DOM Model:
  



A Content Ref is a structure describing a reference to an external configuration that’s used by the BOM and tools around the BOM.
The hash of a content ref (used for calculating content hashes) is the blob sha - representing the version used when deploying elements.


A BOM Element is an abstract construct, the interface of any object in the BOM. Its name uniquely identifies it, globally, across versions; i.e. two BOM elements with the same name in different BOM documents are referring to the same real world object (they might have different content hashes).
An element’s contentHash represents the state of the element in this BOM. It should reflect the state of all attributes in this element that affect the behavior of the system.


A Deployment Functor is a BOM element that represents the function (unit) used to deploy a set of elements.
A functor’s content hash represents the combined state of all elements deployed using that functor in this BOM.


A Deployed Element is a BOM element that’s deployed/applied in the system, affecting its functionality in some way. It can be a code entity deployed but also a feature flag (/set of flags) applied to the system.
A deployed element’s changeContext represents the transient information used in its deployment process that somehow affects the functionality/deployment of the element.
A deployed element’s inventoryRef represents the reference to the inventory configuration used when deploying this element. 
A deployed element’s functorRef represents the reference to the functor version used to deploy this element (effectively changing the system).
The content hash for a deployed element represents the state of the element in the system. It includes the functor and inventory references.


An Artifact-based Element is a deployed element that also has an explicit artifact that’s deployed and affects the state of the system. It has an artifactRef which points to the location and version of the artifact used.
The content hash of an artifact-based element includes, on top of the other attributes, also the artifact ref of the element.

  WITH latest_and_oldest AS (

             FIRST_VALUE(id) OVER (ORDER BY created_at DESC) AS latest_id,
             FIRST_VALUE(id) OVER (ORDER BY id ASC) AS oldest_id
      FROM BOM_DOCS
      WHERE name = 'staging8'
  )
  SELECT 
      CASE 
          WHEN latest.content_hash != oldest.content_hash THEN 'Different'
          ELSE 'Same'
      END AS comparison_result,
      latest.id AS latest_id,
      latest.name,

      oldest.id AS oldest_id,

      oldest.content_hash AS oldest_content_hash
  FROM latest_and_oldest latest
  JOIN latest_and_oldest oldest ON latest.latest_id = latest.id AND oldest.oldest_id = oldest.id

CREATE OR REPLACE FUNCTION calculate_element_hash(
    p_artifact_ref_blob_sha VARCHAR,

BEGIN

    END IF;
    
    RETURN MD5(COALESCE(p_artifact_ref_blob_sha, '') || ':' || COALESCE(p_functor_version, '') || ':' || COALESCE(p_inventory_ref_blob_sha, ''));

-- Function to calculate functor hash from its elements with validation
-- TODO: consider whether this should include the functor version.
CREATE OR REPLACE FUNCTION calculate_functor_hash(functor_id INTEGER) 
RETURNS VARCHAR AS $$
DECLARE
    new_hash VARCHAR;
    element_count INTEGER;
BEGIN
    IF functor_id IS NULL THEN
        RAISE EXCEPTION 'Functor ID cannot be NULL';
    END IF;


    -- Check if functor exists
    IF NOT EXISTS (SELECT 1 FROM bom_FUNCTORS WHERE id = functor_id) THEN
        RAISE EXCEPTION 'Functor with ID % does not exist', functor_id;
    END IF;


    -- Get count of elements for this functor
    SELECT COUNT(*) INTO element_count
    FROM bom_ELEMENTS
    WHERE functor = functor_id;


    -- Calculate hash based functor name and on elements if they exist
    SELECT MD5(CONCAT(f.name, COALESCE(e.content_hashes, '')))
    INTO new_hash
    FROM bom_FUNCTORS f
    LEFT JOIN (
      SELECT functor, string_agg(content_hash, '' ORDER BY name) as content_hashes
      FROM bom_ELEMENTS
      WHERE functor = functor_id
      GROUP BY functor
    ) e ON f.id = e.functor
    WHERE f.id = functor_id;
    RETURN new_hash;
END;
$$ LANGUAGE plpgsql;




-- Function to calculate BOM hash with validation
CREATE OR REPLACE FUNCTION calculate_bom_hash(bom_id INTEGER)
RETURNS VARCHAR AS $$
DECLARE
    new_hash VARCHAR;
    functor_count INTEGER;
BEGIN
    IF bom_id IS NULL THEN
        RAISE EXCEPTION 'BOM ID cannot be NULL';
    END IF;


    -- Check if BOM exists
    IF NOT EXISTS (SELECT 1 FROM BOM_DOCS WHERE id = bom_id) THEN
        RAISE EXCEPTION 'BOM document with ID % does not exist', bom_id;
    END IF;


    -- Get count of functors for this BOM
    SELECT COUNT(*) INTO functor_count
    FROM bom_FUNCTORS
    WHERE document = bom_id;




    SELECT MD5(CONCAT(d.name, COALESCE(f.content_hashes, '')))
    INTO new_hash
        FROM bom_docs d
        LEFT JOIN (
          SELECT document, string_agg(content_hash, '' ORDER BY name) as content_hashes
          FROM bom_functors
          WHERE document = bom_id
          GROUP BY document
        ) f ON d.id = f.document
        WHERE d.id = bom_id;
    RETURN new_hash;
END;
$$ LANGUAGE plpgsql;




-- Main trigger function for ELEMENTS with validation
CREATE OR REPLACE FUNCTION update_element_hashes() 
RETURNS TRIGGER AS $$
DECLARE
    functor_id INTEGER;
    bom_id INTEGER;
    new_functor_hash VARCHAR;
    new_bom_hash VARCHAR;
    new_element_hash VARCHAR;
BEGIN
    -- Validate functor reference
    IF TG_OP IN ('INSERT', 'UPDATE') THEN
        IF NEW.functor IS NULL THEN
            RAISE EXCEPTION 'Functor reference cannot be NULL';
        END IF;
        IF NOT EXISTS (SELECT 1 FROM bom_FUNCTORS WHERE id = NEW.functor) THEN
            RAISE EXCEPTION 'Referenced functor % does not exist', NEW.functor;
        END IF;
    END IF;


   
    IF TG_OP = 'INSERT' OR TG_OP = 'DELETE' OR
          (TG_OP = 'UPDATE' AND 
            (COALESCE(OLD.artifact_ref_blob_sha, '') != COALESCE(NEW.artifact_ref_blob_sha, '') OR
            COALESCE(OLD.functor_version, '') != COALESCE(NEW.functor_version, '') OR
            COALESCE(OLD.inventory_ref_blob_sha, '') != COALESCE(NEW.inventory_ref_blob_sha, ''))) THEN


        -- Calculate new element hash
        new_element_hash := calculate_element_hash(NEW.artifact_ref_blob_sha, NEW.functor_version, NEW.inventory_ref_blob_sha);
        
        -- Update the element's content_hash
        NEW.content_hash := new_element_hash;
        functor_id := COALESCE(NEW.functor, OLD.functor);
    END IF;


    -- Calculate and update hashes if needed
    IF functor_id IS NOT NULL THEN
        -- Calculate new functor hash
        new_functor_hash := calculate_functor_hash(functor_id);
        
        -- Update functor hash
        UPDATE bom_FUNCTORS 
        SET content_hash = new_functor_hash
        WHERE id = functor_id
        RETURNING document INTO bom_id;
        
        -- Calculate and update BOM hash if parent exists
        IF bom_id IS NOT NULL THEN
            new_bom_hash := calculate_bom_hash(bom_id);
            
            UPDATE BOM_DOCS 
            SET content_hash = new_bom_hash
            WHERE id = bom_id;
        END IF;
    END IF;


    RETURN CASE TG_OP 
        WHEN 'DELETE' THEN OLD
        ELSE NEW
    END;
EXCEPTION WHEN OTHERS THEN
    -- Log the error and re-raise
    RAISE WARNING 'Error in update_element_hashes: %', SQLERRM;
    RAISE;
END;
$$ LANGUAGE plpgsql;




-- Trigger function for FUNCTORS with validation
CREATE OR REPLACE FUNCTION update_functor_hashes() 
RETURNS TRIGGER AS $$
DECLARE
    new_bom_hash VARCHAR;
    relevant_doc INTEGER; 
BEGIN
    -- Validate parent reference
    IF TG_OP IN ('INSERT', 'UPDATE') AND NEW.document IS NOT NULL THEN
        IF NOT EXISTS (SELECT 1 FROM BOM_DOCS WHERE id = NEW.document) THEN
            RAISE EXCEPTION 'Referenced BOM document % does not exist', NEW.document;
        END IF;
    END IF;


    -- Only proceed if content_hash changed
    IF (TG_OP = 'UPDATE' AND 
        COALESCE(OLD.content_hash, '') != COALESCE(NEW.content_hash, '')) OR 
        TG_OP IN ('INSERT', 'DELETE') THEN
                relevant_doc := COALESCE(NEW.document, OLD.document);
                new_bom_hash := calculate_bom_hash(relevant_doc);
                
            UPDATE BOM_DOCS 
            SET content_hash = new_bom_hash
            WHERE id = relevant_doc;


    END IF;


    RETURN CASE TG_OP 
        WHEN 'DELETE' THEN OLD 
        ELSE NEW 
    END;
EXCEPTION WHEN OTHERS THEN
    -- Log the error and re-raise
    RAISE WARNING 'Error in update_functor_hashes: %', SQLERRM;
    RAISE;

Data Snapshots
Data Snapshots


Motivation is to have reproducible data sets.


Use Cases
* Create a snapshot of a specific table/collection at a point in time.
   * Should include all data of the table/collection - a complete snapshot.
   * Also the option for partial data (a partial snapshot).
      * i.e. with projection and/or filter.
* Define a “composite snapshot” - a set of snapshots.
   * Usually defined by the db they belong to.
      * For databases defined in the inventory.
   * Snapshots of collections at a specific point in time.
   * May include a subset of tables/collections.
* Store and refer to composite snapshots.
* Load composite snapshots into an existing database.
   * Complete initialization (delete all and load)
   * Snapshot overwrite (leave existing data, but overwrite data if it’s in the snapshot).
      * Could be complex. Maybe at the table level.
      * Lower priority.
* Combine composite snapshots
   * * Combine data snapshots with BOM
   * Apply a BOM
   * Apply a composite snapshot.




Things to consider
* Referential integrity between different databases.
* Schema validation (and evolution).
* PII and generally private data.
Conceptual View




  







A given database snapshot is always in the context of a given entity ⇒ the snapshot has exactly one owner entity. Note a given entity may be the owner of more than one snapshot definition.
The owner entity maintains a definition of the data snapshot (a data snapshot spec). This describes how to create the data snapshot and how to load it.


Data Snapshot Creation Specification
The owner entity maintains a definition of how to create the snapshot. 
This includes:
1. A definition of how to extract the data. One definition per table/collection extracted 
   1. The schema of the snapshot (per table/collection).
      1. We extract all fields. Will support projection in the future if needed.
   2. Filter fields/columns and relevant field values.
      1. Mongo-migrate and Prisma migrate support filtering data.
2. An ordered list of migration scripts for schema and data of the DB.


Connecting Data Snapshots to BOM Elements
We assume:
1. A given entity maintains a list of migration scripts to evolve the data used by the entity.
These migration scripts should include both schema changes[4] and data changes. DB migration tools are described here.
2. Migration scripts are totally ordered. So when applied, they are applied in order to whatever DB they run on.
   3. BOM elements representing DB deployments are uniquely identified (as in the platform inventory), and linked to the owning entity’s BOM element.
   4. In cases where a strict schema is maintained, i.e. postgres, we can distinguish between the schema changes and data changes.
   5. For MongoDB databases we don’t care so much about schema changes[c] (there’s no schema). Migration scripts mainly take care of index definitions.


A data snapshot then refers to the relevant DB BOM element (=BOM elements denoting deployment of databases).

In the absence of DB BOM elements, the snapshot metadata should reference the relevant DB in the platform inventory.


The data snapshot then maintains the last migration applied when it was taken.

Points to note:
   1. The lifecycle of a data snapshot is separate from that of the BOM. It’s possible to deploy a snapshot to a system, as long as the entities deployed there match the data. 
The purpose of the link to the BOM element is to maintain a reference to the owning entity, and to the corresponding migration scripts needed.
   2. The data_snapshot_spec.entity_name should identify the owning identity. It should have the same value as bom_elements.artifact_ref_location.
   3. The data_snapshot_spec.db_name identifies the database this spec refers to. It assumes the db ownership is set up correctly in the platform inventory for the relevant entity.
   4. The data_snapshot_specs.name should be unique. We can have several specifications for the same entity, but each should be easily identified.
   5. The data_snapshots.last_migration_id is the last migration run for a db. It should be taken from a database of migrations that is kept for each db. Link to description.




Deploying a Data Snapshot

Reconstruction of the snapshot then involves:
      1. Deploying the DB element (or connect to an existing one).
      2. Running all schema migration changes.
      3. Loading data
      1. Data in the snapshot conforms to the schema after migration scripts have run.

Duplicating an Environment
One scenario to be addressed is that of duplicating a working environment. This involves both duplicating the versions of the deployed code (the BOM), as well as relevant data.
Deploying a specific BOM is already covered here.


In order to re-create the environment from a data point of view we require:
      1. Understanding which data snapshots were deployed to that environment.
      1. This is per database, per entity.
      2. Alternative, create a snapshot of the existing data.
      2. Deploying all the relevant snapshots.


Understanding which data snapshots are deployed requires having a log of data snapshots deployment to environments. This is the point of the data_snapshot_deployment_log.
